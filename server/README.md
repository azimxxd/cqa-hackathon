# Server core

Node.js ≥ 22.13, Express, встроенный `node:sqlite`. Запуск из корня:
`npm install`, `npm test`, `npm start`. Настройки загружаются из локального `.env`.
По умолчанию БД — `data/cqa.db`; `CQA_DB_PATH` задаёт другой файл.
Первая версия чек-листа — `shared/checklist.default.json`; новые создаются через
`POST /api/checklists`. Версии неизменяемы. При `na_allowed:true` требуется
непустой `na_condition`.

## Импорт

`POST /api/import {"group_id":"DEV"}` делает GET на `ORG_API_URL`, добавляя
query-параметр `group_id`. Нужен `isSuccess:true`. Основная оболочка —
`data.records`, затем поддерживаются `conversations`, `data.conversations`, `data`.
В записи сообщения читаются из `messages ?? transcript`.

Явные таблицы соответствий пока содержат каналы `agent chat`, `voice call` и роли
`client`, `operator`, `bot`, `system` без переименования. Иные значения отклоняются
с указанием поля и значения. Проверить иные обозначения по локальному
`data/dev.json` пока невозможно: файла нет; тесты используют синтетические записи.

Chat timestamp: `MM:SS` или `HH:MM:SS`. Voice timestamp: ISO 8601 с `Z`, `+05:00`
или `+0500`. Исходные timestamp сохраняются; `offset_sec` считается от первой
реплики. Порядок не сортируется: нарушение хронологии сообщает conversation_id
и стабильный ID сообщения (`m001`, …).

Весь пакет атомарен. Повтор неизменённых данных безопасен. Для изменённых записей
под существующими ID ответ — HTTP 409 с полным массивом `conflict_ids`;
новые записи из этого пакета также не сохраняются.
Отсутствующий/неверный URL → 503, сетевая ошибка → 502, таймаут 30 с → 504,
HTTP-ошибка организаторов → 502, не-JSON при 200 → 502,
`isSuccess != true` → 502 с `body.error`, неверные записи → 502.

## Очередь, ошибки и повторы

`POST /api/evaluate {conversation_ids:[...]|"all", checklist_version_id}` → HTTP 202
`{job_id}`. `GET /api/jobs/:id` → `{status,done,total,errors}`; `done` включает
успешные и ошибочные попытки оценки диалогов. Ошибки содержат conversation_id.

- `LLM_CONCURRENCY=6`: общая параллельность.
- `LLM_RETRIES=1`, `LLM_BACKOFF_MS=1000`: сервер повторяет только ошибки с
  `retryable:true`, не более заданного числа повторов.
- Gemini сам делает до `GEMINI_MAX_ATTEMPTS=4` HTTP-попыток на запрос. Задержка
  экспоненциальная от 2 с, с учётом секунд или HTTP-даты `retry-after`, с потолком
  `GEMINI_MAX_BACKOFF_MS=30000`. После последней попытки задержки нет.
- Ollama: до 3 HTTP-попыток на сетевые ошибки/5xx/429, задержка от 500 мс,
  потолок `OLLAMA_MAX_BACKOFF_MS=3000`.
- Ошибки провайдеров сохраняют `status`, `provider`, `retryable`; 4xx, кроме 429,
  имеют `fatal:true`. Некорректный JSON HTTP-оболочки фатален и тоже журналируется.
- ИИ делает ровно один повтор с feedback для невалидных результатов. Если он
  не помог — `invalidResult:true`, IDs, детали, `partial`, `calls`; сервер
  такой ответ повторно не запрашивает и не сохраняет. Ответы/баллы не подставляются,
  поля `needs_review` нет. c08 `no` не требует диапазона; обратный диапазон
  отклоняется до сохранения.

Максимум HTTP-попыток на диалог при полностью невалидных ответах и временных сбоях:
`2 × GEMINI_MAX_ATTEMPTS × (1 + LLM_RETRIES)`, по умолчанию **16**;
для Ollama — `2 × 3 × (1 + LLM_RETRIES)` = **12**. Множитель 2 — один повтор
валидации внутри ИИ, повторно запускаемый только после временной ошибки.
При постоянном 429 валидационного повтора нет: Gemini **8**, Ollama **6**.
Каждая HTTP-попытка имеет строку `llm_calls`, включая неуспешные. Для сетевых и
HTTP-ошибок без usage записываются нулевые токены/расчётная стоимость; стоимость
по ответу с usage учитывает и thinking tokens. Валидация после HTTP не теряет лог.

`CQA_FAKE_LLM=1` явно включает `FAKE`: модель и версия `fake`, нулевая стоимость,
результаты отделены от настоящего кеша. По умолчанию используется `ai/evaluate.js`.
Модель и версия берутся из его экспортов `modelName()` и `PROMPT_VERSION`;
`PROMPT_VERSION` из окружения игнорируется. `options.model/promptVersion` остаются
тестовыми переопределениями. Название Ollama включает префикс `ollama/`.

## Кеш и восстановление

У сервера один кеш — `criterion_results`. Вызов ИИ получает `{noCache:true}`;
ни дисковый, ни memCache ИИ не читаются и не заполняются сервером.
Ключ: `(conversation_id, criterion.hash, prompt_version, model)`.
В колонке `prompt_version` для c06 хранится `${PROMPT_VERSION}|frt=${threshold}`;
для других критериев — `${PROMPT_VERSION}|frt=independent`. Это позволяет
при изменении порога переоценить только c06. Порог по умолчанию — 180 с.

Хеш обеих частей: `sha1(JSON.stringify([title,type,description,na_condition ?? null,
scale ?? null]))`. Вес, `na_allowed`, `gross_error` не входят в хеш; повторно
используемый ответ всегда валидируется по текущим правилам. Невалидный кеш,
включая повреждённый JSON и N/A после его запрета, становится промахом: модель получает только эти
критерии. Вес пересчитывается без вызовов. Производные хеши старых версий
пересчитываются при чтении; старые записи кеша становятся промахами без миграции
и удаления сохранённых оценок. В кеш идут только `original` успешных оценок;
решение проверяющего не переносится в новую Evaluation.

В каждом item (`jobs.data`) фиксируются модель и `prompt_key`; те же параметры
сохраняются в `evaluations.model` и `evaluations.data.prompt_key`. При восстановлении
незавершённой задачи смена модели/версии завершает item ошибкой:
«модель/версия промпта изменились с момента постановки; поставьте оценку заново».
Старые items без зафиксированных настроек также требуют повторной постановки.
Готовая Evaluation имеет приоритет над незаписанным статусом job: повторной записи
результатов нет, `final` проверяющего сохраняется. Сбой во время внешнего вызова
всё ещё может привести к повтору HTTP при следующем запуске.
SIGTERM/SIGINT ждут активных обработчиков; не начатая очередь сохраняется.
Поддерживается один процесс без внешнего брокера.

## Апелляции и статистика

Решение `change` принимает `new_answer`, `new_scale_value`, необязательные
`new_evidence_ids` и `new_checked_range:{from,to}` (или null). Результат проверяется
тем же `validateResult`, что ИИ-ответ. Если поля не переданы, сохраняются прежние;
для `no` без диапазона сервер может вывести окно из существующих evidence.
Ошибки проверки → 400 без частичного решения. `original` неизменен; `final`,
решение и статус апелляции меняются одной транзакцией. Повторное решение и
дублирующая открытая апелляция → 409. Список апелляций возвращает объединение
окон ±2 сообщения вокруг evidence и концов диапазона.

`GET /api/stats`:

| Поле | Значение |
|---|---|
| `calls` | Количество строк `llm_calls` (HTTP-попыток) |
| `tokens` | Входные + выходные токены, включая thinking |
| `cost_usd` | Расчётная стоимость всех записанных попыток |
| `avg_latency_ms` | Среднее время одной HTTP-попытки |
| `avg_cost_per_eval` | Совместимость: вся стоимость / число evaluation_id с вызовами |
| `evaluations_done` | Число Evaluation со статусом done, включая кеш |
| `evaluations_with_calls` | Число Evaluation с хотя бы одной строкой llm_calls, включая error и частичные |
| `avg_cost_per_full_eval` | Сумма затрат на полные оценки / их число; неудачные попытки включены, частичные и полностью кешированные исключены |

Полная оценка: в модели запрошены все критерии версии и есть хотя бы один
записанный вызов. Объём запроса хранится в `evaluations.data.evaluated_criteria`
и `full_eval`, даже при ошибке. Исторические оценки без этих метаданных в новую
метрику полных оценок не входят. При пустом знаменателе — 0.
Eval считает стоимость по тому же определению; ошибки учитывает как промахи.

## Проверки

`npm test` включает настоящий модуль ИИ с Gemini-стабом, общий табличный тест
валидаторов, импорт/ошибки/атомарность, кеш/повторы, восстановление, апелляции,
стоимость и метрики. Все внешние сервисы подменяются.
`node server/verify-start.js` проверяет `npm start` и health на временной БД.
`node scripts/e2e-stub.js` проверяет импорт records → оценку двух диалогов →
апелляцию → веса без LLM → замену текста только c04 → порог только c06 → рестарт.
`npx -y node@22.13.0 --test` проверяет минимальную поддерживаемую версию Node.
