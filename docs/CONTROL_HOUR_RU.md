# Жюри за ноутбуком и 10 новых контрольных чатов

Подготовлено 8 ноября 2026. Все команды выполнять из папки проекта.

## Что уже подготовлено

- Пользовательский критерий можно добавить через редактор: название,
  проверяемое описание, тип, вес, условие N/A и при необходимости шкала.
- Новая версия сохраняет старую. При наличии совместимого кеша добавление
  девятого критерия запускает модель только для нового правила.
- Официальный контрольный запуск выбирает совместимую официальную версию,
  даже если жюри только что создало пользовательскую. Явный выбор несовместимой
  версии останавливается до импорта и оценки.
- `auto` теперь проверяет локальную модель перед выбором и фиксирует
  провайдера на запуск. Раньше отдельная CLI-команда не запускала эту проверку
  и могла выбрать Gemini без проверки доступного Ollama.
- Поддержан исходный JSON из файла через `--input`, в дополнение к API.
- Есть быстрая проверка `npm run preflight` и живая синтетическая репетиция
  `npm run rehearsal -- --live`.
- Для защиты используется отдельная база `data/jury-demo-v18.db` с оценками DEV.
  Для репетиции подготовлен отдельный пример апелляции и замены c07. Команды
  и фразы для выступления собраны в [сценарии на троих](PITCH_5_MIN_RU.md).

## 1. Что отдать жюри

Запуск отдельной копии на ноутбуке:

```sh
CQA_DB_PATH=data/jury-demo-v18.db PORT=3001 npm start
```

Открыть `http://localhost:3001`. Если экземпляр уже отвечает, повторно запускать команду не нужно.
Это отдельная база, но модель и API-ключи берутся из того же `.env`.
Новые оценки из интерфейса используют настоящую модель и её лимиты.

Порядок для жюри:

1. Открыть существующий диалог и перейти от обоснования к реплике.
2. Открыть «Редактор чек-листа» → добавить критерий.
3. Задать конкретное правило и сохранить новую версию.
4. Выбрать **новую версию** для оценки. Если карточка открыта на старой версии,
   переключить её: версия, по которой оценивается карточка, имеет значение.
5. Оценить один диалог и показать результат нового критерия.
6. При желании подать апелляцию и принять решение в режиме проверяющего.

Не начинайте с переоценки всех 65 диалогов: для проверки нового правила хватит
одного подходящего примера. Если жюри хочет всю выборку, пакетная очередь есть,
но нужно дождаться её завершения.

**Готовый пример нового правила:**

| Поле | Значение |
|---|---|
| Название | Срок следующего ответа после передачи обращения |
| Тип | Да / Нет |
| Вес | 10 |
| Описание | Да — оператор сообщил конкретный срок следующего ответа поддержки после передачи обращения коллегам. Нет — сообщил о передаче, но срок не назвал. Проверяется обещание оператора, а не пожелание клиента. |
| N/A | Разрешено |
| Условие N/A | Оператор не сообщал о передаче обращения коллегам. |

Это правило проверено на новых синтетических RU/KZ/EN-примерах с ответами
«да», «нет» и N/A. Новый критерий должен оцениваться по доступным репликам:
правило «клиент потом заработал деньги» нельзя проверить по чату без внешних данных.

Пользовательские 9 критериев не являются официальным форматом сдачи из 8.
Это ожидаемое разделение: свободное демо сохраняет свои версии, контрольный
прогон использует официальный чек-лист. Если организаторы **официально**
изменят формат сдачи, потребуется согласовать и изменить экспортный контракт.

## 2. Почему новые чаты обрабатываются без обучения

Модель получает текст нового разговора и активные правила в каждом запросе.
Ни ручная разметка DEV, ни известные DEV-ID для штатной оценки не нужны.
ID сообщений создаются из порядка реплик; доказательства проверяются по
реально импортированному тексту.

Кеш учитывает исходный текст, модель, версию промпта и конфигурацию.
Нельзя незаметно использовать оценку другого текста. Для новых ID оценок
в базе нет — они проходят полный анализ.

Это обеспечивает работу процесса на новых данных **в поддержанном формате**.
Это не обещание безошибочных смысловых оценок на любом разговоре.
Особенно сложны неоднозначные правила, неполные диалоги, смешение языков
и проверка условий продукта, которых нет в доступных правилах.

## 3. До выдачи контрольных данных

1. На компьютере/сервере, где реально будете оценивать, выполнить:

   ```sh
   npm run gpu:connect  # на ноутбуке, если используете Qwen через Brev
   npm run preflight
   ```

   Проверка показывает фактическую модель и официальный чек-лист. Она не
   импортирует выборку и не запускает генерацию. Для Gemini успешная проверка
   метаданных не гарантирует доступную квоту генерации.

   Облачный резерв можно проверить отдельно командой
   `LLM_PROVIDER=gemini npm run preflight`.

2. Один раз заранее провести живую репетицию:

   ```sh
   npm run rehearsal -- --live
   ```

   Десять синтетических чатов, девять критериев, настоящая модель. В облаке
   расходуется API. Результат — `data/control-rehearsal.json` и датированная
   копия рядом; это не файл сдачи и не независимый тест точности.

3. Зафиксировать выбранную модель и настройки. Для предсказуемости использовать
   `LLM_SAMPLES=1`; преимущество тройного голосования на контроле не доказано.
   Не менять промпт посреди контрольного прогона без конкретной ошибки.

4. Если планируете Qwen, поднять и прогреть сервер **до** выдачи данных.
   В GPU-документации отмечен возможный холодный старт до 20–30 минут.
   Если хотите гарантированно использовать Qwen, поставить `LLM_PROVIDER=ollama`;
   для Gemini — `LLM_PROVIDER=gemini`. `auto` может выбрать облако.

5. Убедиться, что организаторам передана ссылка на открытый репозиторий,
   а финальный код и DEV-файл видны на `main`. Открыть GitHub и проверить
   доступ без авторизации. Проверить право push до выдачи данных.

## 4. Когда пришли 10 чатов: план на час

| Время | Действие | Кто |
|---|---|---|
| 0–5 минут | Получить точный group_id/исходный файл; проверить модель | Участник 3 |
| 5–20 минут | Запустить импорт и оценку в отдельной контрольной базе | Участник 3 |
| 20–35 минут | Проверить ошибки, новые флаги и спорные основания; при необходимости повторить неуспешные | Участники 2 и 3 |
| 35–45 минут | Проверить 10 исходных ID, 80 результатов по критериям, итоговый формат | Участники 1 и 3 |
| 45–60 минут | Передать файл разрешённым способом и убедиться в получении | Участник 1 |

Это резерв времени, а не обещание, что модель обязательно закончит за 15 минут.

**Если данные доступны по API:**

```sh
CQA_DB_PATH=data/control.db npm run prod -- --group_id=ТОЧНЫЙ_ID --source=original
```

**Если дали JSON-файл:** сохранить неизменённый исходник в
`data/control-input.json`, затем:

```sh
CQA_DB_PATH=data/control.db npm run prod -- --group_id=ТОЧНЫЙ_ID --input=data/control-input.json --source=original
```

Вместо `ТОЧНЫЙ_ID` подставить выданное организаторами значение. Если файл
не содержит group_id и организаторы его не выдали, сначала выяснить нужную
метку набора; не выдавать придуманный ID за официальный.

Принимаются API-конверт `isSuccess/data/records` либо массив исходных записей
с `conversation_id`, `channel`, `language`, `transcript`/`messages`.
Поля реплик — `speaker`, `timestamp`, `text`; для чатов время `MM:SS` или
`HH:MM:SS`, сообщения в хронологическом порядке. Произвольный CSV, скриншоты
или другой JSON требуют адаптации; не переименовывайте файл в надежде на импорт.

Обе команды выполняют импорт → проверку 10 чатов → модель → проверку
актуальности → экспорт → валидацию. По умолчанию повторяются отсутствующие,
ошибочные и устаревшие оценки. Полностью повторять успешную выборку не нужно.

**Результаты:**

- `results/prod/results.json` — официальный файл.
- `results/prod/results.json.provenance.json` — модель, промпт, версия правил,
  конфигурация, ID оценок и контрольные суммы.
- `data/prod-<group_id>.json` — сохранённый исходник; специальные символы
  group_id в имени заменяются на подчёркивание. Точный путь печатается при импорте.

`--source=original` означает исходную оценку модели. Проверяющий может
исследовать спорные ответы, но исправления через апелляции не подменят этот
выбранный источник сдачи. Если регламент требует финальные решения человека,
выбрать `--source=final` явно.

Повторная проверка файла по **точному пути исходника из вывода импорта**:

```sh
npm run submission:validate -- results/prod/results.json --dataset=PROD --source=data/prod-ТОЧНЫЙ_ID.json
```

Чтобы посмотреть контрольную базу в интерфейсе после прогона:

```sh
CQA_DB_PATH=data/control.db PORT=3002 npm start
```

Открыть `http://localhost:3002`. Не запускать параллельно переоценку той же
выборки через интерфейс и команду: это создаёт лишние модельные вызовы.

## 5. Отправка до стоп-кода

Приложение к гайду требует commit **и push** обоих JSON в открытый
репозиторий. После проверки PROD, находясь на актуальной ветке сдачи:

```sh
git status --short
git add results/prod/results.json
git diff --cached --stat
git commit -m "submission: add official control results"
git push origin HEAD:main
git ls-remote origin refs/heads/main
```

Сверить SHA с `git rev-parse HEAD`. Открыть на GitHub
`results/dev/results.json` и `results/prod/results.json` на `main`.
Проверить 65 и 10 записей и сообщить организаторам SHA, если они его
запрашивают. Не добавлять `.env`, исходные транскрипты, БД или подписанный
URL. Файл происхождения PROD хранить локально, если он содержит закрытый
идентификатор группы. После стоп-кода оценку и смену чек-листа можно
выполнять на уже зафиксированном коде.

## 6. Если что-то пошло не так

| Ситуация | Действие |
|---|---|
| После жюри появились новые правила | Команда `prod` сама выберет совместимую официальную версию. Для просмотра/демо новые правила сохраняются. |
| Локальная модель выключена | Не тратить контрольный час на ожидание холодного старта. Использовать заранее проверенный доступный провайдер; затем повторить команду. Смена модели делает прежние оценки устаревшими. |
| API организаторов недоступен | Если исходник уже сохранён полностью, повторить с `--input=<путь>`. Не заменять его DEV-данными. |
| Прислали не 10 чатов | Проверить файл/group_id. Не обходить это флагом `--force` без выяснения состава. |
| Одно сообщение не соответствует формату | Посмотреть ошибку импорта; согласовать правильный формат. Не удалять реплику: это меняет доказательства. |
| Отдельный ответ модели невалиден | Повторить обычную команду: успешные актуальные оценки сохранятся, неуспешные будут оценены снова. |
| Висит локальная модель | У Ollama тайм-аут одной попытки может достигать 10 минут, есть повторы. Отследить доступность заранее; при остановке команды и смене провайдера повторить запуск. Не ждать весь час без контроля прогресса. |
| Лимит Gemini | Перейти на заранее проверенный доступный локальный режим либо дождаться разрешённого восстановления квоты. Не считать наличие ключа достаточным. |
| Команда завершилась с ошибкой, но results.json существует | Это может быть предыдущий файл: при неуспехе он намеренно сохраняется. Сверить время, группу и ID в provenance; старый файл не сдавать. |
| Времени не осталось, часть оценок не готова | `--allow-errors` допускает честные error-строки, если это разрешено регламентом. Это неполный результат, а не исправление качества; применять только осознанно. |

## 7. Фактическая репетиция при подготовке

В начале подготовки отсутствовал SSH-туннель с ноутбука до Brev. После
восстановления соединения `auto` снова выбирает Qwen на L40S. Для облачного
резерва на ноутбуке настроена Gemini 3.6 Flash. Расшифровка использует
Gemini 3.1 Flash-Lite.

- Первый прогон на Gemini 3.1 Flash-Lite с v16: **9/10**, один технически
  невалидный ответ по c05 — отсутствовал обязательный диапазон при «нет».
- В v17 уточнено общее требование: диапазон обязателен для любого обычного
  отрицательного бинарного ответа, в том числе при явном нарушении эмпатии.
  Баллы и ответы не подставляются кодом; ошибка исправляется самой моделью.
- Повторный прогон v17: **10/10**, 90 структурно валидных результатов,
  совпали ожидаемые ответы по новому критерию и флагу грубой ошибки.
  Время **28,957 секунды**, расчётная API-стоимость **$0,034224** по настроенным ставкам.
- Первый прогон стоил расчётно $0,034929; два прогона вместе ≈$0,069153.
- Повторили сценарий v17 на восстановленном GPU с Qwen и на Gemini 3.6 Flash.
  Обе модели обработали **10/10** чатов без ошибок. Ожидаемые ответы по новому
  критерию и флагу грубой ошибки совпали. Время составило примерно 79 и 71
  секунду соответственно.

Десять коротких синтетических чатов не доказывают 100% точности на контроле,
а 90 валидных ответов не означают, что проверены все 90 смысловых суждений.
Финальный DEV экспортирован отдельно на Qwen/v18. Прежние **96%** относятся к
отчёту Qwen/v16. Результаты против старой разметки команды доступны в
`results/dev/quality-summary.json`. В ней часть правил интерпретировалась иначе.

На финальной версии облачный резерв Gemini 3.6 Flash обработал **10/10**
синтетических чатов за 94 секунды. Расчёт по настроенному тарифу составил
около **$0,017 за диалог**, с учётом всех вызовов в этом прогоне.

Первый и второй отчёты сохранены отдельно в `data/`; реальные DEV/PROD-
результаты этими синтетическими данными не заменялись.

После изменений: **147/147 автоматических тестов**, проверка запуска и
сквозной сценарий с тестовым провайдером прошли. Отдельный тест проверяет
добавление девятого критерия с повторным использованием исходных восьми;
другой — контрольный экспорт после правок жюри и импорт новых ID из файла.
